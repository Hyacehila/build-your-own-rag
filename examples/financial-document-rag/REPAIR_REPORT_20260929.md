## 结论与验证边界

本轮已修改本地源码、共享配置、回归测试和诊断工具。保留 v2 事实、已发布的两个 LFS SQLite、800 token 切片及 embedding 模型配置；没有修改参考答案，没有提交或推送 Git。

向量距离计算和全文检索仍使用 SQLite；本轮没有引入另一套向量数据库，也未合并朋友尚未回传的内存矩阵加速源码。

修复了结构切片命中后从整节点开头回读的问题，将 C 改为保留原片段的增量增强，扩大原文预算并分离搜索预览预算，为模型输出和工具参数提供最多五次重试，为 D 增加证据缺口提示和初始原文阅读。A/B/C/D 现在有明确的处理路径区别，但不能据此保证准确率单调递增。

真实 API 诊断执行了 4 道题、计划 16 份回答，完成 10 份后服务返回 HTTP 402。DeepSeek 官方将该状态定义为余额不足；本地请求账本尚未到上限。10 份成功答案的 judge 请求也全部受此阻塞。因此本报告不发布新的四组正确率，不把余额错误归因于检索方法，也不宣称已解决原实验所有 HTTP 400。需要原实验的详细错误记录才能定位其根因。

## 1. 四组现在分别做什么

| 组 | 原始证据 | 回答控制 |
|---|---|---|
| A | RRF 后的 PDF 原生文字切片 | 一次生成；不自动扩为整页、不自动添加图片 |
| B | 命中结构片段及原表行/表头，必要时原页图 | 所有高排名命中先读取，再用剩余预算扩展同章节上下文 |
| C | 保留 B 全部片段，额外加入整表摘要和图片描述的检索入口 | 按资产来源分组；摘要命中回到原片段/图像，摘要不能成为引用证据 |
| D | 与 C 相同的索引、原文服务和原文预算 | 先读两个来源，再围绕缺失的公司、年份、指标、单位和计算条件主动查询 |

上一轮 A 会读取整页和图像，本轮 A 按本次要求改成原始切片直接回答。新旧成绩属于不同方案及预算，不能只用准确率差值证明某个单点修复的贡献。正式运行必须使用新的 run ID。

## 2. B：从“命中节点”改成“先读命中片段”

旧阅读器未使用片段定位，结构命中经常转成整节点从零开始读取；窗口还先读前邻居。发布库只读检查确认存在这个行为，但没有发现关联的单个节点超过 8,000 token，因此不能把历史全部退化归因于单节点截断。

本轮处理：

- 新增 `fragment` 模式，读取已保存的原始切片文字和来源，保留表头、命中行及标题上下文；不会把 `raw.orig` 偏移直接套用到规范化的节点文字上。
- B/C 先遍历高排名命中，再用 `context` 模式扩展邻居；邻居不再抢占尚未读取的目标片段预算。
- 表格片段命中按来源分组，但保留组内匹配片段，默认可读三个原始片段；不会仅保留一个代表入口后丢失其余匹配行。
- 每次读取有局部上限，返回 `next_offset`、原始 `chunk_id` 和节点标识；片段续读按片段偏移执行，避免再次从整节点开头读。
- 多页表格行没有精确到页的定位时，文字覆盖率仍采用保守规则；原页图实际读取后才计入相应图像证据覆盖。

涉及：[sources.py](src/financial_rag/sources.py)、[readback.py](src/financial_rag/readback.py)、[runner.py](src/financial_rag/runner.py)。

## 3. C：增量增强及来源分组

旧 C 在检索索引中移除了 B 的表格/图片入口，用生成描述替代，原始事实虽仍在，但精细检索入口丢失。

现在 `enrichment.retrieval_mode = "additive"`：原始片段逐字保留，生成描述作为额外入口。`replace` 仅保留为显式消融配置。模式进入增强索引的版本校验，旧替换索引不能静默当作新索引使用。

融合后按同一图表的资产 ID 分组，采用该组最佳片段的 RRF 分数，不把同一来源重复累加成额外投票。正文不同片段不按整页强行合并，以免丢掉同页的独立证据。

摘要命中会按问题词项选择对应资产的原始片段；没有文字入口的图片仍可回读原始节点和页面图。生成描述自身禁止铸造证据 ID。这里的词项排序是简单的局部定位策略，不是经过验证的语义 reranker。

检索模式本身不进入描述生成缓存键，因此仅切换 additive/replace 可复用相同配置的描述。**本轮 chat 的输出上限也有变化，旧摘要是否可复用仍取决于完整模型和增强参数身份，不能承诺朋友的旧缓存全部命中。**原始片段 embedding 仍按原文本与 embedding 身份复用。

涉及：[enrichment.py](src/financial_rag/enrichment.py)、[chunking.py](src/financial_rag/chunking.py)、[retrieval.py](src/financial_rag/retrieval.py)。

## 4. D 与 API：预算、提示词、重试及故障诊断

### 预算与检索参数

| 参数 | 原共享配置 | 本轮共享配置 |
|---|---:|---:|
| 切片目标 / 重叠 | 800 / 100 | 800 / 100，保持 |
| 稀疏 / 向量候选 | 30 / 30 | 50 / 50 |
| RRF 常数 | 60 | 60 |
| 融合后输出上限 | 无显式最终上限 | 20 个来源组 |
| Direct 命中读取上限 | 10 | 20 |
| 原文预算 | 8,000，预览也扣减 | 24,000，独立于预览 |
| 搜索预览 | 每条 80 | 每条 120，所有搜索合计最多 3,000 |
| 原页图片上限 | 4 | 8，A 不自动用图 |
| 单次读取上限 | 剩余全部预算 | 2,400，避免单个来源耗尽预算 |
| D 逻辑模型轮次 / 工具操作 | 6 / 8 | 10 / 20 |
| chat 最大输出 token | 8,192 | 16,384 |
| judge 最大输出 token | 2,048 | 8,192 |

24,000 是项目 tokenizer 估算的原文预算，并非整个请求长度；图像、元数据、模型推理输出和多轮重复传输仍会增加实际用量。单次读取上限用于分配更大的总预算，而非限制所有上下文只能有 2,400 token。

候选数与最终上下文大小分开配置。Elastic 的官方 RRF 文档将候选窗口与最终 size 分开，并使用默认常数 60；Azure 文档在语义重排场景建议提供 50 个候选。这支持选取 50 作为试验起点，但本项目没有 Azure 语义重排器，因此不能照搬成“最优超参数”。来源：[Elastic RRF](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)、[Azure hybrid query](https://learn.microsoft.com/en-us/azure/search/hybrid-search-how-to-query)。

### Agent 提示与来源标识

D 先读原文，之后要求针对具体缺失项查询：哪个公司、哪个年份、哪个指标、哪个计算操作数尚无证据。比较题必须覆盖各方，计算前检查单位、时间口径、符号和脚注；证据充分即结束，证据不足明确说明。

搜索结果压缩掉重复边框等元数据，同时保留文档版本映射及零基页号。提示词明确文档名称不是节点 ID，读取时必须从 chunk、node、document+page 三类目标中只选一类。没有实际原文证据的最终答案不能直接视为成功完成。

### 重试契约

- JSON、答案结构、引用 ID 和工具参数在执行工具前验证；最多重试五次，即首次请求加五次重试共六次。
- 使用单一重试边界，内部 HTTP 重试关闭，避免“外层六次 × 内层六次”的放大。
- 可恢复的 HTTP 408/429/5xx 按 role 的 retries 处理；当前 chat/vision/judge 设置为五次。
- HTTP 400/401/402 等确定性错误不会盲重试五次。402 后还会在当前工作库会话中阻止同一账号的后续角色请求，避免余额错误反复消耗请求；恢复余额后在新进程继续。
- 最终回答和 judge 可启用 JSON object 模式；工具调用阶段不强加最终答案 JSON 模式；保持模型返回的 reasoning_content 历史。
- 每个物理请求记录状态码、耗时、用量、验证尝试编号；错误信息保存受限的 code/type/param/request_id 和请求结构，不保存密钥或原始错误正文。
- D 的逻辑模型轮数不等于付费请求数：每轮可能有重试，必须查看 API 用量记录。

依据：[DeepSeek JSON 输出](https://api-docs.deepseek.com/guides/json_mode/)、[工具调用](https://api-docs.deepseek.com/guides/tool_calls/)、[思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)、[错误码](https://api-docs.deepseek.com/quick_start/error_codes/)。

涉及：[api.py](src/financial_rag/api.py)、[config.py](src/financial_rag/config.py)、[config.toml](config.toml)。

## 5. 评估、版本与诊断工具

保留首次检索 NDCG/Recall，新增全部搜索页并集的 `search_union_recall`；它用于检查后续检索是否补充相关页，不代表跨轮最终排序。实际阅读覆盖率仍单独统计。旧结果缺少新字段时显示不可用，不补造零分。

新增 [diagnose_retrieval_repairs.py](tools/diagnose_retrieval_repairs.py)。它使用真实问题和原始 PDF，按 B 检索结果轮流选少量图表做增强，保留完整原片段语料。部分增强索引带 `diagnostic_only` 标记，且不会设置为正式当前索引；正式 run 拒绝这类索引。标签只在回答阶段结束后供评分使用，不输入清洗、增强或 Agent。

工具要求显式 `--live` 才调用模型，限定最多八题、十二个增强资产和六十次生成/评分物理请求，embedding 单独统计。已经存在的输出目录不能覆盖。完整答案、证据、工具轨迹、使用配置、代码指纹及用量保存在被忽略的本地目录。

### 参考答案的复核疑点

- 题 0：参考答案用全年回购 18.841 billion 判断超过 30 billion 的一半，但问题可能指 7 月开始的新计划。读取的表格包含年末剩余额度 19.326 billion、第三/第四季度合计 10.674 billion。A/D 区分了全年与新计划口径；B 给出的另一个推算也需要核查。应人工明确问题口径，不能强迫所有回答追随参考结论。
- 题 1：参考答案说 Bank of America Series B 的投票权未说明；实际读取的物理第 191 页明确有与普通股逐股相同的投票权。四组均报告了这一点。需要核验原页及参考标签，不能把包含额外有效证据的答案自动判错。
- 题 44：A/B 都给出新的 20 billion 回购计划，与参考答案的核心金额一致。这是人工文本核对，不替代盲评或正式评分。

所有原始标签保持不变。后续应将“按原基准评分”与“经独立原页复核后的争议清单”分开报告。
