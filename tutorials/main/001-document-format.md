# 001 · 什么样的数据格式，适合成为 RAG 的事实层？

上一章：无 · [返回总目录](../../README.md#主线教程目录) · 下一章：[从不同文件格式到 DoclingDocument](002-docling-document.md)

## 为什么第一章先聊数据格式

我想从数据清洗开始写这个教程。在我做过的几个 RAG 项目里，这一直是最值得花时间的部分之一。不过第一篇先不讲怎么解析 PDF，也不比较 OCR 模型。开始清洗之前，我更想明确一件事：清洗结束后，我们到底希望留下什么？

同一份资料，可以变成一段很长的文本、一组带标题的 Markdown，也可以成为一个记录章节、表格、图片和位置的文档对象。这些结果都能拿去做检索，但它们留给后续系统的选择不同。如果我们只保存了文本，后来想按章节切片、读取表格的表头、找到图片所属的小节，就得重新解析原始文件，或者让模型从剩下的文字里猜。

我希望提供一个统一且高效的事实层，保留清楚的来源与结构，为后续调整切片、结构索引或采用知识图谱留下空间。

本章使用 ViDoRe V3 Finance 数据集中的摩根大通 2024 年报。后续章节也会从这份财报和相关问题中选取材料，讨论解析、切片、检索与回读。读完后，你应该能够判断一份文档对象保留了什么、丢掉了什么，并理解为什么我偏爱 DoclingDocument 这样的表示。前置知识只需要基本的文档层级概念以及 JSON Pointer 的相关概念。

## 拍平一份文档，会丢掉什么

从[摩根大通 2024 年报](https://huggingface.co/datasets/vidore/vidore_v3_finance_en/blob/main/pdfs/jpmorgan_chase_2024.pdf)的 PDF 物理第 220 页开始。页面上有一张表，列出带降级触发条件的场外及清算场外衍生品净应付款，以及相关抵押品。它属于衍生工具附注中的流动性风险部分。

表里的 `15,371` 是 2024 年底净衍生品应付款的公允价值，单位是百万美元。只留下这个数字，就不知道它属于哪一年、哪项指标，也看不到表格限定的合同范围。表格需要保留行列和表头，图片需要保留图注和正文中的说明，段落与表格也需要知道自己属于哪个章节。人阅读时会自然利用这些关系，而把整个文档压平，再按固定大小切片，可能会丢失这些关系。

Markdown 的标题符号、列表边界、表格和图片引用都可以提供结构。把它当成字符串按固定长度切开时，需要考虑如何继续保存和使用这些结构。

扁平数组也可以表达文档结构：如果每个元素保留类型，另外有父子关系和阅读顺序，系统仍然能还原结构。保存后的数据应当能回答“这一段属于哪里”和“它和什么内容有关”。

## 我会用哪些标准判断一种格式

对于将要进入 RAG 的数据，我更关心下面这些问题。

| 判断标准 | 我希望从数据中知道什么 |
| --- | --- |
| 内容保留 | 原文究竟说了什么，是否有缺失、替换或无法识别的部分？ |
| 类型明确 | 这是标题、段落、列表项、表格、图片，还是图注？ |
| 关系完整 | 谁属于谁，先读什么，哪些元素需要放在一起理解？ |
| 来源可追溯 | 来自哪份文件、哪个版本、哪个位置？ |
| 增强可辨认 | 哪些是原文内容，哪些由规则或模型补充？ |
| 下游可复用 | 改切片、索引或检索方案时，是否还能使用这份数据？ |

内容保留意味着我们要忠实于原文，不应该有 LLM 带来的幻觉；类型明确则是希望我们区分不同的数据格式，它们可能需要不同的处理方式；关系完整意味着保留文档的层级结构，让我们可以找到某个节点的同级节点或父子节点。

来源追溯则是希望能够回到原始文档，并进行必要的校验，避免数据过时影响结果；增强可辨认与内容保留相互配合，增强可以进入事实层，但必须区分原文与补充内容，记录来源并检查；下游可复用则要求我们构建的事实层具备一定的通用性。我目前这样组织事实层，就是为了支持后续不同的变种。

本章所说的事实层，是系统采用的、可以追溯到来源的文档记录。它并不保证现实中的事实一定如此。原文可能过时，两个来源可能互相矛盾，解析器也可能识别错误。把它们保存清楚，才方便后续判断与修正。

## 为什么我偏爱 DoclingDocument

DoclingDocument 是 Docling 提供的统一文档表示。在[官方说明](https://docling-project.github.io/docling/concepts/docling_document/)里，它既表达内容类型，也表达层级、阅读顺序和来源位置。我喜欢它的原因是，这些信息可以在同一个对象中关联起来，同时又不必全部塞进一大段正文。

先看它如何组织数据。文字、表格、图片分别放在 `texts`、`tables`、`pictures` 等集合中；`body` 作为正文树的根，通过引用组织这些元素。`groups` 可以表达列表等容器，标题节点也可以直接成为其他元素的父节点，并不要求每一章都必须建成一个 group。

| 部分 | 在本章中关注的作用 |
| --- | --- |
| `texts` | 保存标题、正文、列表项、图注等有文字内容的元素 |
| `tables` | 保存表格及其单元格、行列位置、表头标记等结构 |
| `pictures` | 保存图片节点，关联图片资源与图注 |
| `body`、`groups` | 组织正文与容器；`children` 的先后顺序参与表达阅读顺序 |
| `self_ref`、`parent`、`children` | 定位节点，连接父子关系 |
| `origin`、`pages`、`prov` | 保存格式所能提供的来源、页面及元素位置信息 |

比如 `#/texts/4`，表示从当前 JSON 对象的 `texts` 数组中取索引为 4 的元素。树里的 `children` 保存这样的引用，被引用的内容仍然只在对应集合中存放。既能按结构遍历，也能按元素类型查看，不需要为每一种访问方式复制一遍正文。

下面从这份年报的一次已整理结果中摘出表格节点的定位信息，省略其他字段。节点编号只在这份文档对象及其版本内有意义；重新解析或整理后，编号可能不同。

```json
{
  "self_ref": "#/tables/150",
  "label": "table",
  "parent": { "cref": "#/texts/3131" },
  "prov": [{ "page_no": 220 }]
}
```

这里的父节点 `#/texts/3131` 是“Liquidity risk and credit-related contingent features”，再向上是“Note 5 - Derivative instruments”。不同序列化方式可能把引用字段写成 `cref` 或 `$ref`；重点是引用指向同一份对象中的节点。

表格和图片会比纯粹的文本更复杂。这里的 `15,371` 位于数据行的 2024 年列；同一行的 2023 年值是 `14,655`。行名、列名、单位和表格适用范围需要一起保留。对于图片，我们至少需要知道原图在哪里、原文如何描述它，以及它出现在哪个章节。

位置字段则要尊重输入本身。PDF 可以有页码和坐标，Markdown、HTML 或 Word 的最终分页未必固定。上面的页码来自解析结果，还需要对照原页检查，不能因为字段存在就认为它准确。PDF 物理页码与财报印刷页码也可能不同。

### 从金融文档对象到原文回读

下面省略其他节点，沿本次整理结果中的父子关系展开：

```text
body
└── Notes to consolidated financial statements
    └── Note 5 - Derivative instruments
        └── Liquidity risk and credit-related contingent features
            ├── #/texts/3132  正文
            ├── #/texts/3133  正文
            ├── #/tables/150  净衍生品应付款表
            └── #/texts/3134  下一张表的说明
```

表格的父级链是 `#/tables/150` → `#/texts/3131` → `#/texts/3065` → `#/texts/2707`，来源记录指向物理第 220 页。表格、前后的正文与所属章节分别是节点，可以按关系一起读取，而不必把整份年报压成一段文字。

检索时，切片帮助系统找到这张表；回读时再沿来源引用取得表格及其上下文。这样，最终回答可以核对原文、年份和单位，不需要把切片当作唯一剩下的文档。

这棵树来自解析和结构整理，仍需与原页对照。本章先理解希望保留的对象，后面再讨论如何从复杂文件中获得它。

## 事实层与检索层

处理文档时，我会保留原始文件，再检查解析结果和标题层级。需要补充结构时，可以使用规则或让模型辅助，但要保留正文顺序，标明补充内容的来源，并对照原文检查。

在这套方案里，**事实层和检索层严格分离并控制更新**。原始文档是追溯的起点，整理后的文档对象和检索资料都保留来源关系。出现问题时可以沿途检查：是原始文档就这么写，还是结构整理出了问题？是转换时丢了关系，还是检索读取了错误的上下文？如果只留下最后一个索引库，这些区别就很难再看清。

在查询阶段，我希望检索结果先定位到来源，再读取来源内容供回答使用。检索层可以用 LLM 生成增强内容，但需要保留到事实层的关联，让回答基于事实层。

**对事实层进行增强则需要严格检查。** 模型可能给一段只是提出疑问的讨论起一个肯定式标题，也可能把适用于某个阶段的经验总结成通用结论。正文一字未改，新标题却已经改变了读者和后续系统理解它的方式。因此，事实层的信息增补应严格控制并注明来源，记录哪些标题来自原文、哪些由规则整理、哪些由模型补出。

一个 RAG Demo 可以在几十分钟内跑起来，而理解各个环节并保留来源，能帮助我们在出错时查找原因、着手修改。这也是我从事实层开始讨论的原因。

## 样例说明与小结

回到财报物理第 220 页，先找到净衍生品应付款表，再确认行标题、两个年度和“百万美元”的单位。比较两个值时，还要带上表格的适用范围。接下来几章会沿同一份来源讨论切片、检索和回读。

进入下一步之前，用几个问题作为本章的收尾：

- 原始资料还在吗，能和转换结果对照吗？
- 元素类型、阅读顺序和关系是否真的保留下来了？
- 哪些结构来自原文，哪些经过了整理或生成？
- 定位信息能否指向确定版本，而不是一个碰巧存在的编号？
- 换一种切片或检索方式，是否还得从头猜结构？

先想清楚要留下什么，再去讨论如何从复杂输入里把这些信息拿出来，然后才是将信息交给下一阶段的系统。
