# 001 · 什么样的数据格式，适合成为 RAG 的事实层？

上一章：无 · [返回总目录](../../README.md#主线教程目录) · 下一章：[从不同文件格式到 DoclingDocument](002-docling-document.md)

## 为什么第一章先聊数据格式

我想从数据清洗开始写这个教程。在我做过的几个 RAG 项目里，这一直是最值得花时间的部分之一。不过第一篇先不讲怎么解析 PDF，也不比较 OCR 模型。开始清洗之前，我更想明确一件事：清洗结束后，我们到底希望留下什么？

同一份资料，可以变成一段很长的文本、一组带标题的 Markdown，也可以成为一个记录章节、表格、图片和位置的文档对象。这些结果都能拿去做检索，但它们留给后续系统的选择不同。如果我们只保存了文本，后来想按章节切片、读取表格的表头、找到图片所属的小节，就得重新解析原始文件，或者让模型从剩下的文字里猜。

我希望拥有一个统一且高效的事实层，在提供完整的内容的同时保留清楚的来源与结构，为后续调整切片、索引或构建知识图谱留下空间。

本章使用 ViDoRe V3 Finance 数据集中的摩根大通 2024 年报。后续有几章也会从这份财报和相关问题中选取材料，讨论解析、切片、检索与回读。读完后，你应该能够判断一份文档对象保留了什么、丢掉了什么，并理解为什么我偏爱 DoclingDocument 这样的表示。前置知识只需要基本的文档层级概念以及 JSON Pointer 的相关概念。

## 拍平一份文档，会丢掉什么

从[摩根大通 2024 年报](https://huggingface.co/datasets/vidore/vidore_v3_finance_en/blob/main/pdfs/jpmorgan_chase_2024.pdf)的 PDF 物理第 220 页开始。页面上有一张表，列出带降级触发条件的场外及清算场外衍生品净应付款，以及相关抵押品。它属于衍生工具附注中的流动性风险部分。

表里的 `15,371` 是 2024 年底净衍生品应付款的公允价值，单位是百万美元。如果只留下这个数字，就不知道它属于哪一年、哪项指标以及单位，也看不到表格限定的合同范围。表格需要保留行列和表头，图片需要保留图注和正文中的说明，段落与表格也需要知道自己属于哪个章节。人阅读时会自然利用这些关系，而把整个文档压平，再按固定大小切片，可能会丢失这些关系。

Markdown 的标题符号、列表边界、表格和图片引用可以提供结构。把它当成字符串按固定长度切开时，需要考虑如何继续保存和使用这些结构。扁平数组也可以表达文档结构。只需要每个元素保留类型，另外补充父子关系和阅读顺序。

RAG 需要处理的文件格式繁多，如何把他们统一解析，构建统一的事实内容。如何在清洗文档，构建事实内容结构的时候保留结构内容，而不要把他们彻底压平，导致信息丢失。这就是这一章希望回答的问题。

## 我会用哪些标准判断一种格式

对于如何去清洗将要进入 RAG 的数据，我更关心下面这些问题。

| 判断标准 | 我希望从数据中知道什么 |
| --- | --- |
| 内容保留 | 原文究竟说了什么，是否有缺失、替换或无法识别的部分？ |
| 类型明确 | 这是标题、段落、列表项、表格、图片，还是图注？ |
| 关系完整 | 谁属于谁，先读什么，哪些元素需要放在一起理解？ |
| 来源可追溯 | 来自哪份文件、哪个版本、哪个位置？ |
| 增强可辨认 | 哪些是原文内容，哪些由规则或模型补充？ |
| 下游可复用 | 改切片、索引或检索方案时，是否还能使用这份数据？ |

内容保留意味着我们要忠实于原文，不应该有 LLM 带来的幻觉；类型明确则是希望我们区分不同的数据格式，它们需要不同的处理方式；关系完整意味着保留文档的层级结构，让我们可以找到某个节点的同级节点或父子节点，让机器也能够采用类人的阅读顺序理解文章。

来源追溯则是希望能够回到原始文档，并进行必要的校验，避免数据过时影响结果；增强可辨认与内容保留相互配合，增强可以进入事实层，但必须区分原文与补充内容，记录来源并检查；下游可复用则要求我们构建的事实层具备一定的通用性，包含足够的信息去支撑不同的检索方式。

本章所说的事实层，是系统采用的、可以追溯到来源的文档记录。它并不保证现实中的事实一定如此，原文可能过时，两个来源可能互相矛盾，解析器也可能识别错误。但我们需要这样的一个事实层，一个尽可能可靠的事实层去支持后续的各种衍生系统。

## 为什么我偏爱 DoclingDocument

DoclingDocument 是 Docling 提供的统一文档表示。在[官方说明](https://docling-project.github.io/docling/concepts/docling_document/)里，它既表达内容类型，也表达层级、阅读顺序和来源位置。我喜欢它的原因是，这些信息可以在同一个对象中关联起来，同时又不必全部塞进一大段正文。

先看它如何组织数据。文字、表格、图片分别放在 `texts`、`tables`、`pictures` 等集合中；`body` 作为正文树的根，通过引用组织这些元素。`groups` 可以表达列表等容器，标题节点也可以直接成为其他元素的父节点。

| 部分 | 在本章中关注的作用 |
| --- | --- |
| `texts` | 保存标题、正文、列表项、图注等有文字内容的元素 |
| `tables` | 保存表格及其单元格、行列位置、表头标记等结构 |
| `pictures` | 保存图片节点，关联图片资源与图注 |
| `body`、`groups` | 组织正文与容器；`children` 的先后顺序参与表达阅读顺序 |
| `self_ref`、`parent`、`children` | 定位节点，连接父子关系 |
| `origin`、`pages`、`prov` | 保存格式所能提供的来源、页面及元素位置信息 |

例如，`#/texts/4` 从整个文档对象的根开始，指向 `texts` 数组中索引为 4 的节点。节点通过 `parent` 和 `children` 相互引用，可以从 `body` 出发按层级和子节点顺序遍历，也可以直接查看某一类节点。数组下标用于统计索引元素，这样构建树状索引的时候就可以利用节点索引而不复制节点内容。

下面的例子来自这份年报的一次整理结果。为了看清关系，JSON 片段省略了部分字段、子节点和单元格；`text` 字段中的 `...` 表示长文本被截断。引用字段在这份结果中写作 `cref`，其他序列化方式也可能使用 `$ref`.

### 容器节点：组织文档结构

在这次整理结果中，`body` 下有一个 `#/groups/323` 容器，里面包含财务报表附注的标题：

```json
{
  "self_ref": "#/groups/323",
  "name": "source-range:180",
  "label": "section",
  "parent": { "cref": "#/body" },
  "children": [{ "cref": "#/texts/2707" }]
}
```

这个容器通过 `parent` 连接正文树的根，再通过 `children` 连接标题节点。它用来组织结构，本身不提供正文段落。

### 标题与正文：用引用连接节点

年报中的“Liquidity risk and credit-related contingent features”是一个标题节点，它保存在 `texts` 中：

```json
{
  "self_ref": "#/texts/3131",
  "label": "section_header",
  "level": 3,
  "text": "Liquidity risk and credit-related contingent features",
  "parent": { "cref": "#/texts/3065" },
  "children": [
    { "cref": "#/texts/3132" },
    { "cref": "#/texts/3133" },
    { "cref": "#/tables/150" }
  ],
  "prov": [{ "page_no": 220 }]
}
```

`self_ref` 是这个节点在文档对象中的位置；`label` 表明它是标题，`level` 记录标题层级。它的 `parent` 指向上一级标题“Note 5 - Derivative instruments”，`children` 则依次指向该标题下的段落和表格。这里的列表只摘出了前三个子节点。

沿第一个子引用找到 `#/texts/3132`，就能读到一个正文节点：

```json
{
  "self_ref": "#/texts/3132",
  "label": "text",
  "text": "In addition to the specific market risks...",
  "parent": { "cref": "#/texts/3131" },
  "children": [],
  "prov": [{ "page_no": 220 }]
}
```

这个节点的 `text` 保存段落文字，`parent` 又指回刚才的标题。由此既能从标题找到正文，也能从正文找到所属小节。

### 表格节点：数值和表头一起保存

同一标题下的 `#/tables/150` 是一张表。下面只摘出 2024 年列表头和其中一个金额单元格：

```json
{
  "self_ref": "#/tables/150",
  "label": "table",
  "parent": { "cref": "#/texts/3131" },
  "prov": [{ "page_no": 220 }],
  "data": {
    "num_rows": 3,
    "num_cols": 3,
    "table_cells": [
      {
        "text": "December 31, 2024",
        "start_row_offset_idx": 0,
        "start_col_offset_idx": 1,
        "column_header": true
      },
      {
        "text": "$ 15,371",
        "start_row_offset_idx": 1,
        "start_col_offset_idx": 1,
        "column_header": false
      }
    ]
  }
}
```

两个单元格的列索引都是 1，按从零开始的索引计算，它们位于第二列。结合完整表格中的行名、单位和适用范围，才能知道 `15,371` 是什么；同一行的 2023 年值为 `14,655`，单位均为百万美元。表格结构让系统有机会把这些信息一起读回来，而不是只留下一个孤立的数字。[第二章](002-docling-document.md)会继续解释单元格的位置和跨度。

### 图片节点：位置与图片资源

同一份年报中还有图片节点。例如，下面的 `#/pictures/1` 位于“FIVE-YEAR STOCK PERFORMANCE”标题下：

```json
{
  "self_ref": "#/pictures/1",
  "label": "picture",
  "parent": { "cref": "#/texts/948" },
  "captions": [],
  "image": null,
  "prov": [{ "page_no": 54 }]
}
```

`parent` 帮助我们找到图片所在的小节，`prov` 指向 PDF 物理第 54 页；原节点中还有位置坐标，这里没有展开。`captions` 为空，表示这次结果没有关联图注。

位置字段取决于输入和解析结果：PDF 可以有页码和坐标，Markdown、HTML 或 Word 的最终分页未必固定。即使记录了位置，也需要对照原页检查；PDF 物理页码与财报印刷页码可能不同。

### 从金融文档对象到原文回读

把前面的容器、标题、正文和表格放回整棵树中，就能看到它们的上下文。下图省略了其他内容：

```text
body
└── #/groups/323  文档容器
    └── #/texts/2707  Notes to consolidated financial statements
        └── #/texts/3065  Note 5 - Derivative instruments
            └── #/texts/3131  Liquidity risk and credit-related contingent features
                ├── #/texts/3132  正文
                ├── #/texts/3133  正文
                ├── #/tables/150  净衍生品应付款表
                └── #/texts/3134  下一张表的说明
```

表格的父级链是 `#/tables/150` → `#/texts/3131` → `#/texts/3065` → `#/texts/2707`。表格、前后的正文与所属章节均是节点，可以按关系一起读取，而不必把整份年报压成一段文字。

检索时，切片帮助系统找到这张表；回读时再沿来源引用取得表格及其上下文。这样，最终回答可以核对原文、年份和单位，不需要把切片当作唯一剩下的文档。

## 事实层与检索层

处理文档时，我会保留原始文件，再检查解析结果和标题层级。需要补充结构时，可以使用规则或让模型辅助，但要保留正文顺序，标明补充内容的来源，并对照原文检查。

在这套方案里，**事实层和检索层严格分离并控制更新**。原始文档是追溯的起点，整理后的文档对象和检索资料都保留来源关系。出现问题时可以沿途检查：是原始文档就这么写，还是结构整理出了问题？是转换时丢了关系，还是检索读取了错误的上下文？如果只留下最后一个索引库，这些区别就很难再看清。

在查询阶段，我希望检索结果先定位到来源，再读取来源内容供回答使用。检索层可以用 LLM 生成增强内容，但需要保留到事实层的关联，让回答基于事实层。

**对事实层进行增强则需要严格检查。** 模型可能给一段只是提出疑问的讨论起一个肯定式标题，也可能把适用于某个阶段的经验总结成通用结论。正文一字未改，新标题却已经改变了读者和后续系统理解它的方式。因此，事实层的信息增补应严格控制并注明来源，记录哪些标题来自原文、哪些由规则整理、哪些由模型补出。

一个 RAG Demo 可以在几十分钟内跑起来，而理解各个环节并保留来源，能帮助我们在出错时查找原因、着手修改。这也是我从事实层开始讨论的原因。

## 小结

进入下一步之前，用几个问题作为本章的收尾：

- 原始资料还在吗，能和转换结果对照吗？
- 元素类型、阅读顺序和关系是否真的保留下来了？
- 哪些结构来自原文，哪些经过了整理或生成？
- 定位信息能否指向确定版本，而不是一个碰巧存在的编号？
- 换一种切片或检索方式，是否还得从头猜结构？

先想清楚要留下什么，再去讨论如何从复杂输入里把这些信息拿出来，然后才是将信息交给下一阶段的系统。
