## 为什么第一章先聊数据格式

我想从数据清洗开始写这个教程。在我做过的几个 RAG 项目里，这一直是最值得花时间的部分之一。不过第一篇先不讲怎么解析 PDF，也不比较 OCR 模型。开始清洗之前，我更想明确一件事：清洗结束后，我们到底希望留下什么？

同一份资料，可以变成一段很长的文本、一组带标题的 Markdown，也可以成为一个记录章节、表格、图片和位置的文档对象。这些结果都能拿去做检索，但它们留给后续系统的选择不同。如果我们只保存了文本，后来想按章节切片、读取表格的表头、找到图片所属的小节，就得重新解析原始文件，或者让模型从剩下的文字里猜。

我希望把这些选择尽量留到后面。现在不做结构索引，不代表以后也不需要；今天使用一种切片方式，也不意味着它会一直适合。事实层应该保存足够清楚的来源与结构，让后续方案有调整的余地。无论你想用最传统的切片、结构化索引，还是知识图谱相关技术，我都希望我们能提供一个统一且高效的事实层。

本章使用[金融 RAG 示例](../../examples/financial-document-rag/TEACHING.md)中的三页虚构银行报告。后续理解解析、切片、检索与回读时，也可以继续沿这个项目阅读。读完后，你应该能够判断一份文档对象保留了什么、丢掉了什么，并理解为什么我偏爱 DoclingDocument 这样的表示。前置知识只需要基本的文档层级概念以及 JSON Pointer 的相关概念。

## 拍平一份文档，会丢掉什么

样例是 Example Bank 的三页报告。第一页是业绩段落和收入图，第二页是业务收入表，第三页是风险与流动性说明。公司与数值都是虚构的，只为把问题讲清楚；表中的 `Test segment` 行专门用于长表拆分测试，不参与业务统计。

表里的 `100` 对应 Retail 业务在 2024 年的收入，单位是百万美元。只留下这个数字，就不知道它属于哪个业务、哪个年度，也无法区分收入与现金余额。表格需要保留行列和表头，图片需要保留图注和正文中的说明，业务收入小节也需要知道自己属于业绩章节。人阅读时会自然利用这些关系，而把整个文档压平，并按照一定的 Chunk 大小进行切片，再设置一些 overlap，可能会丢失这些关系。

我反对的是丢失结构，并不是 Markdown 这个格式。Lenny Compass 的输入本身就是 Markdown。标题符号、列表边界、表格和图片引用都可以提供结构；问题在于处理过程中是否继续保存和使用它们。把一份 Markdown 直接当成字符串按固定长度切开，是一种操作选择，不是 Markdown 必然带来的结果。

同样，文件里使用扁平数组，也不等于文档被拍平。如果每个元素保留类型，另外有父子关系和阅读顺序，系统仍然能还原结构。真正值得检查的是：保存后的数据，能否回答“这一段属于哪里”和“它和什么内容有关”。

## 我会用哪些标准判断一种格式

对于将要进入 RAG 的数据，我更关心下面这些问题。

| 判断标准 | 我希望从数据中知道什么 |
| --- | --- |
| 内容保留 | 原文究竟说了什么，是否有缺失、替换或无法识别的部分？ |
| 类型明确 | 这是标题、段落、列表项、表格、图片，还是图注？ |
| 关系完整 | 谁属于谁，先读什么，哪些元素需要放在一起理解？ |
| 来源可追溯 | 来自哪份文件、哪个版本、哪个位置？ |
| 增强可辨认 | 哪些是原文内容，哪些由规则或模型补充？ |
| 下游可复用 | 改切片、索引或检索方案时，是否还能使用这份数据？ |

内容保留意味着我们要忠实于原文，不应该有 LLM 带来的幻觉；类型明确则是希望我们区分不同的数据格式，它们可能需要不同的处理方式；关系完整意味着保留文档的层级结构，让我们可以找到某个节点的同级节点或父子节点。

来源追溯则是希望能够回到原始文档，并进行必要的校验，避免数据过时影响结果；增强可辨认与内容保留相互配合，增强可以进入事实层，但必须区分原文与补充内容，记录来源并检查；下游可复用则要求我们构建的事实层具备一定的通用性。我目前这样组织事实层，就是为了支持后续不同的变种。

本章所说的事实层，是系统采用的、可以追溯到来源的文档记录。它并不保证现实中的事实一定如此。原文可能过时，两个来源可能互相矛盾，解析器也可能识别错误。把它们保存清楚，才方便后续判断与修正。

## 为什么我偏爱 DoclingDocument

DoclingDocument 是 Docling 提供的统一文档表示。在[官方说明](https://docling-project.github.io/docling/concepts/docling_document/)里，它既表达内容类型，也表达层级、阅读顺序和来源位置。我喜欢它的原因是，这些信息可以在同一个对象中关联起来，同时又不必全部塞进一大段正文。

先看它如何组织数据。文字、表格、图片分别放在 `texts`、`tables`、`pictures` 等集合中；`body` 作为正文树的根，通过引用组织这些元素。`groups` 可以表达列表等容器，标题节点也可以直接成为其他元素的父节点，并不要求每一章都必须建成一个 group。

| 部分 | 在本章中关注的作用 |
| --- | --- |
| `texts` | 保存标题、正文、列表项、图注等有文字内容的元素 |
| `tables` | 保存表格及其单元格、行列位置、表头标记等结构 |
| `pictures` | 保存图片节点，关联图片资源与图注 |
| `body`、`groups` | 组织正文与容器；`children` 的先后顺序参与表达阅读顺序 |
| `self_ref`、`parent`、`children` | 定位节点，连接父子关系 |
| `origin`、`pages`、`prov` | 保存格式所能提供的来源、页面及元素位置信息 |

比如 `#/texts/4`，表示从当前 JSON 对象的 `texts` 数组中取索引为 4 的元素。树里的 `children` 保存这样的引用，被引用的内容仍然只在对应集合中存放。既能按结构遍历，也能按元素类型查看，不需要为每一种访问方式复制一遍正文。

下面是教学对象中的业务收入标题节点，省略了其他字段，但保留完整的 `children` 列表。完整对象见[参考 JSON](../../examples/financial-document-rag/reference/document.json)。

```json
{
  "self_ref": "#/texts/3",
  "label": "section_header",
  "text": "1.1 Revenue by business unit",
  "level": 2,
  "parent": { "$ref": "#/texts/0" },
  "children": [
    { "$ref": "#/texts/4" },
    { "$ref": "#/tables/0" }
  ]
}
```

这里的父节点 `#/texts/0` 是“1. Performance”。它的孩子包括业绩段落、图注、收入图和业务收入小节；业务收入小节再引用表格图注 `#/texts/4` 与表格 `#/tables/0`。第三页的“2. Risk and liquidity”则是另一个一级章节，不应挂到业绩章节下面。

表格和图片会比纯粹的文本更复杂。样例中的 `100` 属于哪一列，应该由单元格位置和表头共同说明。在实际对象里，它位于从零计数的第 1 行、第 2 列，对应 Retail 与 `2024 USD m`。对于图片，我们至少需要知道原图在哪里、原文如何描述它，以及它出现在哪个章节。这里的图片节点通过 `captions` 引用 `#/texts/2`，又通过页码和区域定位到原始 PDF 的收入图。

位置字段则要尊重输入本身。PDF 可以有页码和坐标，Markdown、HTML 或 Word 的最终分页未必固定。这个教学对象记录了三页的尺寸，以及节点的物理页和区域；这些信息来自生成夹具时的已知布局。实际解析结果中的位置则需要对照原页检查，不能因为字段存在就认为它准确。

### 从金融教学对象到原文回读

这个小样例的结构已知，因此直接构造 DoclingDocument，让我们先看清最终希望保留的东西。下面省略了其他字段，按实际正文关系展开：

```text
body
├── #/texts/0   1. Performance
│   ├── #/texts/1    业绩段落
│   ├── #/texts/2    收入图图注
│   ├── #/pictures/0 收入图
│   └── #/texts/3    1.1 Revenue by business unit
│       ├── #/texts/4  收入表图注
│       └── #/tables/0 业务收入表
└── #/texts/5   2. Risk and liquidity
    └── #/texts/6    风险与流动性段落
```

表格的父级链是 `#/tables/0` → `#/texts/3` → `#/texts/0` → `#/body`，其来源记录指向物理第 2 页。图注与图表分别是正文节点，又通过 `captions` 关联；这与父子关系不是一回事。完整关系见[参考文档树](../../examples/financial-document-rag/reference/structure.txt)。

运行[教学入口](../../examples/financial-document-rag/TEACHING.md#本地生成与回读)时，程序用同一份夹具构建平面与结构化切片，再按表格节点读取原文。切片是后续检索入口，回读结果保留表格原文及来源页，不需要把切片当作唯一剩下的文档。

真实财报的树不能像夹具这样预先知道，需要经过解析、结构整理与原页检查。金融示例保留了这些环节的实现；本章先理解交付对象，后面再讨论如何从复杂文件中获得它。教学夹具的成功不证明真实 PDF 的解析质量。

## Lenny Compass 以及一些个人经验

Lenny Compass 是我围绕个人订阅资料做的一个 RAG 项目，希望通过大量与产品知识相关的文档，弥补自己在产品方面的能力不足。这里借用的是它组织数据的经验，相关数据不会随教程提供。原始输入主要是 Newsletter 和 Podcast 的 Markdown，格式统一，但标题层级不够完善。

在这个项目里，我保留原始文档，再通过脚本与 LLM 增强和整理结构，之后才转换为 DoclingDocument。我让模型辅助补充章节和小节标题，尽量沿讲话轮次的边界组织内容，同时保留正文顺序；也用脚本整理文档的标题层级结构，避免写作习惯影响 Docling 的解析效果。

在这个系统里，**事实层和检索层严格分离并控制更新**。原始文档的数据是权威来源，整理后的检索层也有对应的来源记录。后续构建切片和查询索引时，系统才能知道这些东西究竟来自哪一份文档。出现问题时可以沿途检查。是原始文档就这么写，还是结构整理出了问题？是转换时丢了关系，还是检索读取了错误的上下文？如果只留下最后一个索引库，这些区别就很难再看清。

在查询阶段，我也希望检索结果先定位到来源，再读取来源内容供回答使用。索引适合找到东西，却不应该悄悄成为唯一剩下的原文。这里不展开切片和索引算法，我们先把可以回去读取的那份数据准备好。

检索层可以相对随意地使用 LLM 进行增强，但**对事实层进行增强是有风险的行为，必须谨慎检查增强带来的幻觉。** 模型可能给一段只是提出疑问的讨论起一个肯定式标题，也可能把适用于某个阶段的经验总结成通用结论。正文一字未改，新标题却已经改变了读者和后续系统理解它的方式。

如果只对检索层进行增强，那大可以随意一些，只要保证每一个检索层都能回到事实层，并让回答基于事实层本身，大概率就没有什么问题。事实层的信息增补应该严格控制并加以注明，记录哪些标题来自原文、哪些由规则整理、哪些由模型补出，避免模型基于幻觉回答，产出不可信的结果。

这也是为什么我们会在第一篇里聊独立事实层，而不是一个 RAG Demo。确实只需要几十分钟就能跑起来一个 Demo，但如果缺乏对整个系统的理解，出了错就很难知道原因，也难以着手修改。

## 样例说明与小结

运行入口与环境要求见[金融教学路线](../../examples/financial-document-rag/TEACHING.md)。不想先安装依赖，也可以直接对照[原始 PDF](../../examples/financial-document-rag/reference/fictional-bank.pdf)和[参考输出](../../examples/financial-document-rag/reference/README.md)阅读。

先找到“1.1 Revenue by business unit”，沿父级读到“1. Performance”；再看表格中的 `100`，确认行标题、年度和单位都还在。随后查看收入图与图注的引用，找到它们在原 PDF 中的位置。运行后对照 `chunks.json` 和 `readback.json`，看看切片提供了什么、原文回读又保留了什么。如果有自己的数据，也不妨对照原页检查相关结果，理解我们会交给后续系统什么样的数据。

进入下一步之前，用几个问题作为本章的收尾：

- 原始资料还在吗，能和转换结果对照吗？
- 元素类型、阅读顺序和关系是否真的保留下来了？
- 哪些结构来自原文，哪些经过了整理或生成？
- 定位信息能否指向确定版本，而不是一个碰巧存在的编号？
- 换一种切片或检索方式，是否还得从头猜结构？

先想清楚要留下什么，再去讨论如何从复杂输入里把这些信息拿出来，然后才是将信息交给下一阶段的系统。
