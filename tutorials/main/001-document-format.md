## 为什么第一章先聊数据格式

我想从数据清洗开始写这个教程。在我做过的几个 RAG 项目里，这一直是最值得花时间的部分之一。不过第一篇先不讲怎么解析 PDF，也不比较 OCR 模型。开始清洗之前，我更想明确一件事：清洗结束后，我们到底希望留下什么？

同一份资料，可以变成一段很长的文本、一组带标题的 Markdown，也可以成为一个记录章节、表格、图片和位置的文档对象。这些结果都能拿去做检索，但它们留给后续系统的选择不同。如果我们只保存了文本，后来想按章节切片、读取表格的表头、找到图片所属的小节，就得重新解析原始文件，或者让模型从剩下的文字里猜。

我希望把这些选择尽量留到后面。现在不做结构索引，不代表以后也不需要；今天使用一种切片方式，也不意味着它会一直适合。事实层应该保存足够清楚的来源与结构，让后续方案有调整的余地。

本章会借用我在 Lenny Compass 中的经验，但所有演示内容都来自一份[原创虚构的产品复盘](../../examples/structured-document-facts/fixtures/product-review.md)，不分发那个项目的真实数据。读完后，你应该能够判断一份解析结果保留了什么、丢掉了什么，并理解为什么我偏爱 DoclingDocument 这样的表示。前置知识只需要基本的文档层级概念；不了解 JSON Pointer 也没关系，后面会用实际对象解释。

## 拍平一份文档，会丢掉什么

样例是一份“星舟协作”的邀请流程复盘。里面有两部分：“新团队邀请实验”和“现有团队权限检查”，它们各有一个叫“观察结果”的小节。前者有邀请实验的指标表，后者解释成员权限没有变化。产品与数值都是虚构的，只为把问题讲清楚。

假设我们拿到“邀请完成率从 40% 变为 55%”，却没有保留它属于哪个实验、适用于哪些团队，也没有保留表里的“7 天内完成首次邀请”这个统计口径。这句话仍然通顺，也很容易被召回。但如果用户问现有团队的表现，系统就可能把它放进不合适的回答里。文本没有识别错，解释它所需的关系却已经丢了。

两个“观察结果”也是同一个问题。单独看标题，无法判断它们分别在讨论什么；保留完整章节路径后，它们才容易被区分。表格需要知道哪一列是“调整后”，图片需要保留图注和正文中的说明，列表项需要知道自己属于哪份清单。人阅读时会自然利用这些关系，我不希望在交给系统之前先把它们删掉。

这里需要说清楚，我反对的是丢失结构，并不是 Markdown 这个格式。Lenny Compass 的输入本身就是 Markdown。标题符号、列表边界、表格和图片引用都可以提供结构；问题在于处理过程中是否继续保存和使用它们。把一份 Markdown 直接当成字符串按固定长度切开，是一种操作选择，不是 Markdown 必然带来的结果。

同样，文件里使用扁平数组，也不等于文档被拍平。如果每个元素保留类型，另外有父子关系和阅读顺序，系统仍然能还原结构。真正值得检查的是：保存后的数据，能否回答“这一段属于哪里”和“它和什么内容有关”。

## 我会用哪些标准判断一种格式

我不会只看导出的预览是否漂亮。对于将要进入 RAG 的数据，我更关心下面这些问题。

| 判断标准 | 我希望从数据中知道什么 |
| --- | --- |
| 内容保留 | 原文究竟说了什么，是否有缺失、替换或无法识别的部分？ |
| 类型明确 | 这是标题、段落、列表项、表格、图片，还是图注？ |
| 关系完整 | 谁属于谁，先读什么，哪些元素需要放在一起理解？ |
| 来源可追溯 | 来自哪份文件、哪个版本、哪个位置？ |
| 增强可辨认 | 哪些是原文内容，哪些由规则或模型补充？ |
| 下游可复用 | 改切片、索引或检索方案时，是否还能使用这份数据？ |

“内容保留”也需要一个边界。结构化对象很难完整复制原文件的一切：排版、字体、页面外观，甚至某些交互行为，未必都能留在同一种表示里。因此我会保留原始快照，让文档对象承担已经明确表达出来的内容与结构。所谓保存完整，需要对照任务和源文件检查，不能因为 JSON 校验通过，就说所有信息已经无损保留。

来源信息同样不是只留一个文件名。文档会修改，解析规则会更新，同名文件可能有不同内容。后面拿着一个节点编号回来时，我们必须知道它属于哪一份对象，否则一次正常的数据更新也可能让旧引用指向错误的位置。

本章所说的“事实层”，是系统采用的、可以追溯到来源的文档记录。它并不保证现实中的事实一定如此。原文可能过时，两个来源可能互相矛盾，解析器也可能识别错误。把它们保存清楚，才方便后续判断与修正；存进一个叫 facts 的目录，不会自动解决真假问题。

## 为什么我偏爱 DoclingDocument

DoclingDocument 是 Docling 提供的统一文档表示。在[官方说明](https://docling-project.github.io/docling/concepts/docling_document/)里，它既表达内容类型，也表达层级、阅读顺序和来源位置。我喜欢它的原因是，这些信息可以在同一个对象中关联起来，同时又不必全部塞进一大段正文。

先看它如何组织数据。文字、表格、图片分别放在 `texts`、`tables`、`pictures` 等集合中；`body` 作为正文树的根，通过引用组织这些元素。`groups` 可以表达列表等容器，标题节点也可以直接成为其他元素的父节点，并不要求每一章都必须建成一个 group。

| 部分 | 在本章中关注的作用 |
| --- | --- |
| `texts` | 保存标题、正文、列表项、图注等有文字内容的元素 |
| `tables` | 保存表格及其单元格、行列位置、表头标记等结构 |
| `pictures` | 保存图片节点，关联图片资源与图注 |
| `body`、`groups` | 组织正文与容器；`children` 的先后顺序参与表达阅读顺序 |
| `self_ref`、`parent`、`children` | 定位节点，连接父子关系 |
| `origin`、`pages`、`prov` | 保存格式所能提供的来源、页面及元素位置信息 |

比如 `#/texts/4`，表示从当前 JSON 对象的 `texts` 数组中取索引为 4 的元素。树里的 `children` 保存这样的引用，被引用的内容仍然只在对应集合中存放。既能按结构遍历，也能按元素类型查看，不需要为每一种访问方式复制一遍正文。

下面是本例实际生成的一个节点，省略了其他字段，但保留完整的 `children` 列表。它是数据格式摘录，不是独立有效的完整文档；完整对象见[参考 JSON](../../examples/structured-document-facts/reference/document.json)。

```json
{
  "self_ref": "#/texts/4",
  "label": "section_header",
  "text": "观察结果",
  "level": 2,
  "parent": { "$ref": "#/texts/2" },
  "children": [
    { "$ref": "#/texts/5" },
    { "$ref": "#/groups/0" },
    { "$ref": "#/groups/1" },
    { "$ref": "#/tables/0" },
    { "$ref": "#/pictures/0" },
    { "$ref": "#/texts/8" },
    { "$ref": "#/texts/9" }
  ]
}
```

这里的父节点 `#/texts/2` 是“新团队邀请实验”。沿着父级继续向上，就能知道这个“观察结果”属于哪篇文档、哪项实验。另一个同名小节是 `#/texts/12`，属于“现有团队权限检查”。标题可以重复，节点与上下文仍然能够区分。

表格也值得单独看。样例中的“55%”属于哪一列，应该由单元格位置和表头共同说明，而不是只剩下几个相邻的字符串。实际对象里，它位于从零计数的第 1 行、第 2 列，同列第 0 行的表头是“调整后”；第 3 列还保留统计口径。更复杂的表格还会有跨行、跨列等信息。格式能表达这些关系，后续处理才有机会利用它们。

图片也类似。我希望至少知道资源在哪里、原文如何描述它、它出现在哪个章节。没有下载图片，就不能说系统看过图片；只有一个图片地址，也不能算完成了图片理解。本例只保留引用和图注，不生成视觉描述。

位置字段则要尊重输入本身。PDF 可以有页码和坐标，Markdown、HTML 或 Word 的最终分页未必固定。我们的 Markdown 样例没有可靠页码，所以对象中的 `pages` 和 `prov` 为空。此时可以回到指定版本的结构节点，但不能据此声称能高亮原文某一页，或者精确定位到源文件某一行。

### 从 Markdown 解析结果到本例保存的事实层

这里需要把转换过程讲清楚：**Markdown 后端返回的已经是 DoclingDocument，但本例保存的事实层对象，还经过了一次显式的结构整理。** 两者是同一种数据格式，不是先得到普通文本，再由我们创造一个 DoclingDocument。上面的 JSON 展示的是整理后的对象。

本例固定使用 `docling-slim==2.120.1`、`docling-core==2.91.0`，通过 Markdown 后端和 `SimplePipeline` 转换输入。后端已经识别出标题、段落、列表、表格和图片等元素，也保存了标题级别与阅读顺序。样例中的一级标题成为 `title`，二级和三级标题成为 `section_header`，其 `level` 分别为 1 和 2；数字与 Markdown 的井号数量不是直接相等的。

但在这条转换路径中，后端没有进一步把后续段落、表格等节点挂到所属标题下面。[对应版本的后端源码](https://github.com/docling-project/docling/blob/v2.120.1/docling/backend/md_backend.py#L342-L344)明确注明，Marko 的语法树没有将章节内容作为标题的子节点，这部分父节点跟踪尚未实现。`SimplePipeline` 直接接收后端生成的对象，不会自动补上这一步。因此，不能把“还没有显式章节树”说成“标题层级没有识别出来”，也不能把这个 Markdown 后端的表现推广到所有输入格式。

以第一张表为例，原始转换对象中的主要节点是这样排列的。图中省略了其他节点，剩余节点仍按原有顺序展示：

```text
body
├── #/texts/0   title：星舟协作：邀请流程复盘
├── #/texts/2   section_header，level=1：新团队邀请实验
├── #/texts/4   section_header，level=2：观察结果
├── #/tables/0  邀请实验指标表
├── #/texts/10  section_header，level=1：现有团队权限检查
└── #/texts/12  section_header，level=2：观察结果
```

表格的 `parent` 是 `#/body`，所以直接查询父节点得不到章节名。不过，顺着阅读顺序看，表格前最近的二级章节是“新团队邀请实验”，其下最近的小节是“观察结果”。标题级别和顺序足以按章节边界推导出这条路径。这就是同一个对象中“已有层级信息”和“已建立父子关系”的区别。

### 下游如何使用这些结构信息

我查到的官方实现提供了一个具体参照：[HierarchicalChunker](https://docling-project.github.io/docling/concepts/chunking/#hierarchical-chunker)按阅读顺序遍历文档，维护当前各级标题，遇到同级或更高层标题时结束相应范围，再把章节路径写入切片的 `meta.headings`。这里使用标题自身的 `level`，不要求段落的直接父节点必须是标题。官方的 HybridChunker 再在这一结果上处理 token 长度等约束。

对同一份材料，可以根据使用目的选择处理位置：

| 目的 | 处理方式 | 得到什么 |
| --- | --- | --- |
| 让切片携带章节上下文 | 在切片时根据标题级别和阅读顺序维护路径，例如官方 HierarchicalChunker | 切片带有 `meta.headings`；源对象不因此自动变成章节树 |
| 直接沿父级读取章节，或按章节遍历子树 | 在保存前把已有层级组织成显式父子关系，这是本例的选择 | DoclingDocument 本身具有可遍历的章节树 |
| 输入连标题级别都缺失或错误 | 先恢复并检查标题与级别，再决定如何组织和使用 | 补齐结构信息；不能靠简单挂接父节点解决识别错误 |

例如 PDF 的标题级别推断属于第三种问题，官方另有[标题级别处理说明](https://docling-project.github.io/docling/usage/heading_levels/)。不能把它当成本例 Markdown 输入需要开启的开关。这些是有实现依据的处理路径，并不意味着所有项目都采用同一种做法。

我也对本例的两个对象做了实际核对：直接把未整理的对象交给官方 HierarchicalChunker，表格切片已经得到“星舟协作：邀请流程复盘 → 新团队邀请实验 → 观察结果”这条路径；整理后的对象得到相同路径。所以这里的整理不是让文档第一次具备结构感知切片的能力，而是让事实层支持我们想要的直接父级回读。

### 本例具体怎么处理，结果是什么

我选择在保存事实层之前做这一步。示例按已有标题级别维护当前章节，把后续节点归入对应标题；遇到同级或更高层级的新标题，就结束前面的相应范围。列表等已有容器保留内部关系，不重新创造标题或修改正文。整理后的主要关系如下：

```text
星舟协作：邀请流程复盘
├── 新团队邀请实验
│   └── 观察结果
│       ├── 结论段落与列表
│       ├── 邀请实验指标表
│       └── 图片引用、图注及说明
└── 现有团队权限检查
    └── 观察结果
        └── 权限说明与列表
```

[适配前的对象](../../examples/structured-document-facts/reference/parsed-document.json)保留后端原始结果；[适配后的对象](../../examples/structured-document-facts/reference/document.json)是本例最终保存与回读的事实层，另有[完整结构树](../../examples/structured-document-facts/reference/structure.txt)供核对。两份对象中，表格仍是 `#/tables/0`，但它的父节点由 `#/body` 变为 `#/texts/4`，再向上依次是 `#/texts/2`、`#/texts/0` 和 `#/body`。它属于哪个章节，现在可以直接沿引用读出来。

Docling Core 2.91.0 自身也有内部方法 `_hierarchize()`；对本例的原始对象调用后，同样能把表格挂到“观察结果”下。因此无需把手写逻辑描述成唯一解决办法。本例保留范围较小、可以检查的标题整理规则，避免让运行入口依赖内部接口；它也不承担任意文档的结构修复。

完整流程是“Markdown → 后端生成 DoclingDocument → 整理已有结构并核对 → 保存最终对象与来源清单 → 按版本回读”。来源清单记录整理规则，文档哈希在整理完成后计算。图片替代文字映射为图注是另一个独立规则，不与章节归属混为一谈。我们需要检查的是每一步实际产出的对象，而不只是文件名里有没有 Docling。

## Lenny Compass 给我的经验

Lenny Compass 是我围绕个人订阅资料做的一个 RAG 项目。这里借用的是它组织数据的经验，相关数据不会随教程提供。原始输入主要是 Newsletter 和 Podcast 的 Markdown，虽然格式统一，标题层级却不一定适合直接拿来使用。

在这个项目里，我保留原始文档，再形成经过结构整理的版本，之后才转换为 DoclingDocument。原始文档的元数据仍有自己的权威来源，整理后的内容也有对应的来源记录。后续构建切片和查询索引时，系统才能知道这些东西究竟来自哪一份文档。

这样的分开保存有一个直接用途：出现问题时可以沿途检查。是原始文档就这么写，还是结构整理出了问题？是转换时丢了关系，还是检索读取了错误的上下文？如果只留下最后一个索引库，这些区别就很难再看清。

保存文档对象也不只是导出一个 JSON。Lenny Compass 会把它重新加载回来，检查序列化前后是否一致，再记录文档与来源的哈希。我们的[独立示例](../../examples/structured-document-facts/README.md)保留了这部分思路：保存原始字节、结构化对象与来源清单，并把定位信息绑定到文档版本。

`#/texts/4` 只对某份具体对象有意义。如果前面插入了新节点，再次转换后同一个地址可能对应其他内容。因此回读时要一起核对文档 ID、文档对象哈希和节点引用。哈希不匹配就应明确失败，而不是因为这个编号仍然存在，就继续返回它。

在查询阶段，我也希望检索结果先定位到来源，再读取来源内容供回答使用。索引适合找到东西，却不应该悄悄成为唯一剩下的原文。这里不展开切片和索引算法，我们先把可以回去读取的那份数据准备好。

## 事实层也可能被增强，但这一步要小心

保留结构听起来很自然，可原始文档未必有足够好的结构。Lenny Compass 中的 Podcast 文档就是一个例子：讲话轮次存在，适合阅读和检索的章节却未必存在。我会让模型辅助补充章节和小节标题，尽量沿讲话轮次的边界组织内容，同时保留正文顺序。

按照我在这个项目里的定义，这属于对事实层的增强，补出的结构会成为事实层的一部分。我不会因为它由模型生成，就一概认为不能使用；但也不能因为它已经写进事实层，就把它当成原文自带的信息。

**对事实层进行增强是有风险的行为，必须谨慎检查增强带来的幻觉。** 模型可能给一段只是提出疑问的讨论起一个肯定式标题，也可能把适用于某个阶段的经验总结成通用结论。正文一字未改，新标题却已经改变了读者和后续系统理解它的方式。

这种错误还会继续传下去。结构感知切片可能把错误标题带入上下文，结构索引可能沿错误分类导航，后续摘要也可能把这个标题当成已确认的结论。结构不是没有内容的外壳，它会影响解释。

因此，我希望保留增强之前的文档，记录哪些标题来自原文、哪些由规则整理、哪些由模型补出，以及它们对应的原文范围。检查时既要确认有没有改变、遗漏或重排正文，也要阅读标题和所属段落是否真的相符。确定性检查能发现一部分问题，但发现不了所有语义偏差；涉及结论、范围和归属的变化仍需要仔细复核。

模型补出的标题可以帮助组织资料，却不能冒充原文标题放进引用里。图片描述、检索摘要等其他增强也应该保留清楚的来源区别。我们可以利用它们帮助找到资料，同时让回答能够说明哪些话来自原文，哪些是系统补充的解释。

本章示例只做基于已有标题的确定性适配，没有实际运行模型增强。讲清风险不等于已经实现了一套可靠的增强审核系统；后面真做清洗时，还需要结合具体材料设计检查办法。

## 保留结构，给后续留下什么

最直接的是切片。既然知道哪些内容属于同一小节，就可以优先沿自然边界处理；需要进一步拆分时，也能够保留章节路径和原始元素引用。表格的表头、图片的图注，至少不会因为存储时已经丢掉而无法找回。具体切多大、何时合并，仍然需要根据任务判断。

结构索引也能利用同一份表示。按标题组织阅读、按元素类型找表格、按元数据筛选文档，都需要先有相应信息。DoclingDocument 表达的是文档对象，真正执行跨文档查询时，仍可以把它投影到关系表、关键词索引或其他检索结构中，不要求直接在一个 JSON 文件上完成所有查询。

进一步构建知识系统或 GraphRAG 时，来源节点还可以成为实体和关系的证据入口。抽取结果来自哪个段落、哪个表格，之后能否回去核对，这些问题不会因为换成图就消失。不过文档树的“属于某一章”和知识图谱里的业务关系是不同东西。实体抽取、消歧、关系定义与更新仍需要另做，保存一棵文档树不会自动得到可信的知识图谱。

这也是我愿意在这一层多花时间的原因：先保留来源和结构，后面才可以尝试不同方法、比较结果，并在发现问题时回到同一份材料。它给我们更多选择，但不保证每一种复杂方案都会带来收益。

## 动手检查这份样例

运行入口与环境要求见[示例说明](../../examples/structured-document-facts/README.md#构建与读取)。不想先安装依赖，也可以直接对照[原始 Markdown](../../examples/structured-document-facts/fixtures/product-review.md)和[参考输出](../../examples/structured-document-facts/reference/README.md)阅读。

先找到两个“观察结果”，检查它们的父级是否不同；再看表格中的“55%”，确认列标题和统计口径都还在。随后查看图片地址、图注，以及适配前后这些关系发生了什么变化。最后尝试拿一个不同文档版本的定位信息回读，观察程序是否明确拒绝，而不是静默返回错误内容。

这套检查不需要评测模型回答得多好。我们此时只检查将要交给后续系统的数据：结构有没有按预期保存，内容与来源能否核对，出错时是否能够发现。

进入下一步清洗之前，我会再问自己：

- 原始资料还在吗，能和转换结果对照吗？
- 元素类型、阅读顺序和关系是否真的保留下来了？
- 哪些结构来自原文，哪些经过了整理或生成？
- 定位信息能否指向确定版本，而不是一个碰巧存在的编号？
- 换一种切片或检索方式，是否还得从头猜结构？

先想清楚要留下什么，再去讨论如何从复杂输入里把这些信息拿出来。对我来说，这就是数据清洗工作的起点。
